# 数据埋点方案 —— 支付转化优化(示例)

| 文档信息 | 内容 |
|----------|------|
| 版本 | v1.1 |
| 状态 | 已评审,待开发接入 |
| 对应流程图 | `../static/数据埋点流程.excalidraw`(第 ② 步产出物) |
| 更新日期 | 2026-11-05 |

## 1. 背景与目标

- **业务背景**:购物车 → 支付成功的转化率约 40%,低于行业水平(约 60%)。
- **分析问题**:用户在结算链路的哪一步流失最多?流失原因是什么?
- **北极星指标**:支付成功率 = 支付成功订单数 ÷ 提交订单数(按 `order_id` 去重),目标从 40% 提升至 60%。
- **过程指标**:漏斗各环节转化率、支付失败原因分布、支付耗时。

## 2. 指标口径定义

| 指标 | 口径 | 级别 | 依赖事件 |
|------|------|------|----------|
| 购物车结算率 | `checkout_click` 去重用户 ÷ `cart_view` 去重用户 | 用户级 | cart_view、checkout_click |
| 订单提交率 | `order_submit` 去重用户 ÷ `checkout_click` 去重用户 | 用户级 | checkout_click、order_submit |
| 支付点击率 | `pay_click` 去重订单 ÷ `order_submit` 去重订单 | 订单级 | order_submit、pay_click |
| 支付成功率 | `pay_success` 去重订单 ÷ `order_submit` 去重订单 | 订单级 | order_submit、pay_success |

> 用户级指标用 `user_id` 关联,订单级指标必须用 `order_id` 关联。

## 3. 公共属性(所有事件默认携带)

| 属性 | 类型 | 必填 | 示例 | 说明 |
|------|------|------|------|------|
| user_id | string | 是 | u_10086 | 登录用户唯一 ID,未登录时用设备匿名 ID |
| device_id | string | 是 | d_ab12cd | 设备唯一标识(SDK 生成) |
| platform | string | 是 | android | 枚举:ios / android / web |
| app_version | string | 是 | 3.12.0 | 客户端版本号 |
| os_version | string | 是 | HarmonyOS 4.2 | 操作系统版本 |
| device_model | string | 否 | Mate 60 Pro | 机型 |
| network | string | 否 | wifi | 枚举:wifi / 4g / 5g |
| channel | string | 是 | huawei_store | 投放/分发渠道 |
| event_time | datetime | 是 | 2026-11-05 10:00:00.123 | SDK 自动打点 |

## 4. 事件明细

### 4.1 `cart_view` 进入购物车页

- **采集端**:客户端 · 代码埋点
- **触发时机**:购物车页面加载完成时(每次进入上报一次)

| 属性 | 类型 | 必填 | 示例 | 说明 |
|------|------|------|------|------|
| item_count | int | 是 | 3 | 购物车内商品种类数 |
| cart_amount | float | 是 | 259.00 | 购物车总金额,单位元,保留两位 |

### 4.2 `checkout_click` 点击"去结算"

- **采集端**:客户端 · 代码埋点
- **触发时机**:点击结算按钮的瞬间

| 属性 | 类型 | 必填 | 示例 | 说明 |
|------|------|------|------|------|
| item_count | int | 是 | 2 | 本次结算商品种类数 |
| order_amount | float | 是 | 199.00 | 结算预览金额(不含运费) |
| coupon_used | bool | 是 | true | 是否使用了优惠券 |

### 4.3 `order_submit` 提交订单

- **采集端**:**服务端埋点**(交易数据以服务端为准,防客户端丢单)

| 属性 | 类型 | 必填 | 示例 | 说明 |
|------|------|------|------|------|
| order_id | string | 是 | o_20261105123 | 订单唯一 ID,贯穿后续支付事件 |
| amount | float | 是 | 189.00 | 订单实付金额 |
| address_province | string | 是 | 广东省 | 收货地址省份(物流分析维度) |
| coupon_used | bool | 是 | true | 是否用券 |
| coupon_id | string | 否 | c_88 | **v1.1 新增**:所用券 ID |
| coupon_amount | float | 否 | 10.00 | **v1.1 新增**:券抵扣金额 |

### 4.4 `pay_click` 点击"立即支付"

- **采集端**:客户端 · 代码埋点
- **触发时机**:点击支付按钮、收银台拉起前

| 属性 | 类型 | 必填 | 示例 | 说明 |
|------|------|------|------|------|
| order_id | string | 是 | o_20261105123 | 订单 ID |
| pay_channel | string | 是 | wechat | 枚举:wechat / alipay / unionpay |
| order_amount | float | 是 | 189.00 | 应付金额 |

### 4.5 `pay_success` 支付成功

- **采集端**:**服务端埋点**(以支付回调为准)

| 属性 | 类型 | 必填 | 示例 | 说明 |
|------|------|------|------|------|
| order_id | string | 是 | o_20261105123 | 订单 ID |
| pay_channel | string | 是 | wechat | 支付渠道 |
| pay_duration_ms | int | 是 | 4300 | 从 `pay_click` 到支付成功耗时 |

### 4.6 `pay_fail` 支付失败

- **采集端**:**服务端埋点 + 客户端兜底**(两端都报,按 `order_id` + 渠道流水去重)

| 属性 | 类型 | 必填 | 示例 | 说明 |
|------|------|------|------|------|
| order_id | string | 是 | o_20261105123 | 订单 ID |
| pay_channel | string | 是 | wechat | 支付渠道 |
| fail_reason | string | 是 | signature_error | 枚举:signature_error / user_cancel / insufficient_balance / timeout / bank_declined / unknown |
| pay_duration_ms | int | 是 | 2100 | 从 `pay_click` 到失败回调耗时 |

## 5. 命名规范

1. 事件名:小写 snake_case,`动宾` 或 `对象_动作` 结构(`cart_view`、`pay_click`);
2. 属性名:小写 snake_case,金额类以 `_amount` 结尾并统一单位为元、两位小数;时长类以 `_ms` / `_s` 结尾并在说明中注明单位;
3. 枚举值:全小写下划线(`signature_error`),新增枚举值须先更新本文档;
4. 事件**只增不删**:废弃事件保留事件名并标记 `deprecated`,避免历史数据断口径。

## 6. 埋点方式与分工

| 事件 | 采集端 | 选择理由 |
|------|--------|----------|
| cart_view / checkout_click / pay_click | 客户端代码埋点 | 需要精确触发时机与前端上下文 |
| order_submit / pay_success / pay_fail | 服务端埋点(客户端兜底) | 交易结果以服务端为准,防丢单、防篡改 |
| 全 App 页面 PV/点击 | 全埋点打底 | 通用行为覆盖,后续分析不必等发版 |

**关联键**:`order_id` 贯穿 4.3–4.6 形成订单链路;`user_id` 串联跨会话用户行为;客户端与服务端数据在数仓按 `order_id` 对账合并。

## 7. 上线前验证 Checklist

- [ ] 调试模式走通「加购 → 结算 → 提交 → 支付 → 成功/失败」全链路,事件触发顺序正确;
- [ ] 必填属性完整率 100%,枚举值全部合法;
- [ ] 金额单位统一为元、两位小数;耗时单位统一为毫秒;
- [ ] 抽样 20 笔订单做客户端/服务端对账,按 `order_id` 匹配差异 ≤ 1 笔;
- [ ] `order_submit` 上报量与业务订单量偏差 ≤ 1%;
- [ ] 弱网/断网重试场景不产生重复上报(SDK 去重验证)。

## 8. 质量监控与告警

| 规则 | 阈值 | 动作 |
|------|------|------|
| 单事件日上报量环比波动 | > ±30% | 企业微信告警到数据值班群 |
| 必填属性完整率 | < 99% | 告警并定位版本/平台 |
| `pay_success` 与支付回调流水偏差 | > 2% | 告警,优先排查 SDK 上报链路 |
| 新版本发布后 24h | — | 重点观察新版事件量与完整率 |
